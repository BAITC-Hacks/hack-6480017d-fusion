# Fusion: OpenAI-аналитик + NVIDIA-рецензент

## Статус и цель

Это план обязательного будущего AI-этапа, а не готовая интеграция. На этапе 1 сохраняется существующий работающий каркас: API, зависимости и интерфейс для AI не подключаются. По уточнённому запросу пользователя оба API должны выполнять полезную работу внутри приложения. NVIDIA больше не является только резервом. Конкретные модели и доступ к ним ещё не проверены; ключи в комплект не включены.

OpenAI готовит справку по выбранному узлу. Модель через NVIDIA NIM проверяет эту справку по исходным фактам, ищет недоказанные утверждения, альтернативные объяснения и пропущенные ограничения. Это потенциальный способ повысить качество объяснений, а не гарантия истинности: обе модели могут ошибаться. Согласие моделей не равно подтверждению подозрения.

## Минимальный пользовательский сценарий

1. Пользователь выбирает узел и нажимает «AI-разбор».
2. Backend формирует ограниченный evidence_packet одного выбранного узла: gid строкой, рассчитанная роль и её правило, role_score, priority_score, числовые признаки, несколько значимых связей, период и caveats. Каждому факту присваивается evidence_id и источник: входная таблица и поле либо название рассчитанной метрики с версией правила. Все gid/src/dst, в том числе в связях, передаются точными строками; числа для ID не допускаются. Пакет имеет явные лимиты числа фактов, соседей и общего объёма. Если связи сокращены, пакет содержит total_neighbors, returned_neighbors и признак сокращения. Источники ссылаются только на локальные данные и расчёты; внешний поиск и обогащение не выполняются.
3. OpenAI получает только этот пакет и выдаёт структурированную справку: hypothesis, claims[{claim_id,text,evidence_ids}], limitations, next_checks. Гипотеза интерпретирует рассчитанные признаки, но не назначает новую роль и не меняет скоры. Основания ссылаются на evidence_id из пакета, ограничения отражают caveats, следующие проверки не выдаются за уже проведённые. Использовать Structured Outputs для выбранной совместимой модели, обрабатывать отказ и неполный ответ.
4. Backend проверяет структуру и ограничения длины ответа, существование ссылок evidence_ids и отсутствие посторонних gid. Числовые значения интерфейс выводит из пакета фактов. Отказ, неполный ответ и невалидная справка считаются ошибкой первого этапа: такой ответ не отправляется рецензенту. Валидная JSON-схема и корректная ссылка ещё не доказывают, что вывод поддержан фактом.
5. Только после успешной валидации справки OpenAI NVIDIA получает тот же пакет, эту справку и задачу искать ошибки. Выдаёт issues[{claim_id,kind,reason,evidence_ids}], alternative_explanations, missing_information. Типы замечаний: unsupported_claim, missing_caveat, overstatement, contradiction. Не требовать, чтобы рецензент обязательно нашёл ошибку; пустой список допустим. Рецензент не меняет роли, скоры, кластеры или CSV. Структурированный вывод и параметры зависят от модели/endpoint: проверить поддержку, иначе запросить JSON и валидировать Pydantic.
6. Backend валидирует рецензию. Показывает «Справка OpenAI» и «Замечания NVIDIA» раздельно. Отмеченные фразы подсвечивает как требующие проверки; не принимает рецензента за арбитра истины. Не выполнять третий вызов для переписывания справки в MVP.

## Что пользователь увидит

- Краткую гипотезу о роли и основания с переходом к фактам/связям.
- Замечания рецензента, возможное обычное объяснение поведения и недостающие сведения.
- Предупреждение о границе наблюдения на depth=4 и неполных входящих seed.
- Отдельный статус каждого этапа: ожидание, выполняется, реальный ответ API, из кеша, ошибка или пропущен. Показывать фактический model ID и измеренное время только состоявшегося вызова; для кеша показывать происхождение сохранённого ответа. Локальная справка имеет отдельную явную отметку «локальная справка (fallback)» и не называется ответом OpenAI или NVIDIA.
- Текст «AI помогает интерпретировать данные; выводы требуют проверки аналитиком».

Иллюстративный сценарий, не результат реального вызова: аналитик предлагает гипотезу накопления, рецензент указывает, что узел на depth=4 и отсутствие исходящих объясняется границей выгрузки. В действующем приложении не фабриковать разногласие для демо.

## Что сохраняется детерминированным

Граф, метрики, роль, role_score, priority_score, кластер и три обязательных CSV вычисляются детерминированным Python-пайплайном локально и не меняются от текста моделей. nodes_roles.csv, clusters.csv и top_nodes.csv воспроизводятся без LLM, интернета и платного API после установки зависимостей. role_score остаётся эвристической поддержкой роли, не вероятностью виновности. ML-тюнинг, голосование моделей за роль, проценты «вероятности преступления» и автоматические решения о блокировке не входят в MVP.

## Интеграция и ограничения расходов

- Два серверных адаптера. OpenAI — Responses API со структурированным выводом; NVIDIA hosted NIM — POST /v1/chat/completions. Не предполагать идентичность всех параметров и возможностей.
- OPENAI_API_KEY, OPENAI_MODEL, NVIDIA_API_KEY, NVIDIA_MODEL, NVIDIA_BASE_URL в серверном .env. Не читать секреты в вывод инструментов, не включать в frontend и логи.
- На нормальный разбор без кеша — ровно два последовательных вызова: OpenAI, затем NVIDIA. На один запуск разбора — максимум два внешних вызова суммарно. Без третьего вызова, циклов агентов, автоматического исправления ответа через модель и скрытых ретраев SDK/HTTP; автоматические повторы отключить явно. Повторные клики во время одного разбора не создают дополнительные запросы. Короткие ответы, один выбранный узел, ограниченный пакет фактов; не передавать весь parquet.
- Целевой таймаут на каждый вызов 20 секунд, общий предел около 45 секунд. Значения проверить и при необходимости уточнить по реальной задержке выбранных моделей, сохраняя конечный общий лимит ожидания.
- Кешировать валидные результаты обоих этапов по хешу набора данных, gid, evidence_packet, версиям правил/промптов и model ID; ключ рецензии дополнительно включает хеш валидированной справки OpenAI. Повторный клик использует кеш; обновление — явная кнопка. Кеш и частичное попадание в него сокращают число вызовов, но не увеличивают лимит. Не кешировать ошибку или локальную справку как успешный ответ провайдера.
- Показывать валидированную справку OpenAI, пока выполняется рецензия. При сбое или невалидном ответе NVIDIA сохранить справку OpenAI с пометкой «рецензия недоступна» и ошибкой NVIDIA. При отсутствии, отказе, таймауте или невалидном ответе OpenAI показать детерминированную локальную справку из тех же фактов; NVIDIA получает статус «пропущен: нет валидной справки OpenAI» и не вызывается. Локальную справку нельзя передавать как якобы ответ OpenAI. Fallback не доказывает успешную работу обоих API.
- Учёт токенов и вызовов по провайдерам; не обещать конкретную стоимость без проверенного тарифа аккаунта. Не оценивать финансовый расход только по заявленному балансу.
- Для NVIDIA рассмотреть доступную через аккаунт модель семейства Nemotron, для OpenAI — модель с Structured Outputs. Окончательный выбор после короткой проверки русского языка, ссылок на факты, задержки и доступа. Максимальный размер модели сам по себе не цель.

## Проверка пользы и сдача

После подключения выполнить реальные вызовы обоих API на 5–6 разных узлах и вручную сравнить справку OpenAI отдельно с той же справкой вместе с замечаниями NVIDIA. В выборку обязательно включить depth=4 и изолированный seed; остальные примеры выбрать среди seed с неполным входом и рассчитанных кандидатов на разные роли. Проверять неподтверждённые факты, пропущенные оговорки, корректность ссылок, ложные замечания рецензента, качество русского языка и задержку. Справка автоматически не переписывается. Это ручная проверка качества объяснений, не измерение accuracy ролей.

При интеграции добавить искусственно ошибочную справку (например «деньги точно остались» для depth=4) как тестовый пример, явно отделённый от реальных результатов. Отдельно проверить timeout, отказ, невалидный JSON и посторонний evidence_id, пропуск NVIDIA после ошибки OpenAI, честность статусов кеша/fallback и соблюдение максимума двух вызовов без скрытых повторов. Не сообщать, что качество улучшено, пока сравнение этого не показало.

Критерий готовности AI-этапа: оба API успешно работают в приложении, оба ответа раздельно отображаются, источники фактов доступны, ошибки не ломают приложение и выполнено описанное сравнение на 5–6 разных узлах. Один успешный узел подтверждает соединение, но ещё не завершает проверку этапа. Mock-тесты не заменяют реальные вызовы; при отсутствии ключей честно отметить интеграцию непроверенной.
