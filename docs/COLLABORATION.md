# Работа команды с Fusion

Репозиторий: https://github.com/BAITC-Hacks/hack-6480017d-fusion.git

Файлы Fusion находятся в корне репозитория. Дополнительная вложенная папка Fusion внутри него не нужна.

## Напарнику

Клонировать в свою локальную папку, например на рабочем столе:

```bash
cd ~/Desktop
git clone https://github.com/BAITC-Hacks/hack-6480017d-fusion.git Fusion
cd Fusion
```

Если папка Fusion уже существует, не клонировать поверх неё: открыть её и проверить git status/remote либо выбрать другую пустую папку. Для push аккаунт GitHub должен иметь права записи в репозиторий команды. Секреты не передавать через Git.

Датасеты в Git не включены согласно настройке проекта. Передать напарнику исходные nodes.parquet, edges.parquet, transactions.parquet из хакатонного комплекта и положить в data/. См. data/README.md. Каждый участник самостоятельно создаёт .venv и устанавливает зависимости по README. Реальный .env каждый настраивает локально; на этапе 1 ключи не нужны.

## Каждый рабочий сеанс

С чистой рабочей папкой:

```bash
git status
git pull --ff-only
```

При одновременной разработке использовать отдельные рабочие папки и разные ветки, например один участник — feature/graph, другой — feature/ui. Название конкретной ветки согласовать по задаче. Первый push: git push -u origin <имя-ветки>; дальше git push. Ветка на GitHub обновляется после каждого промпта с изменениями; main получает завершённые изменения после объединения веток. Не работать одновременно вдвоём в одной физической папке с одним Git index.

Перед завершением каждого промпта: подходящие проверки → просмотр diff → commit → push. Конфликты не решать перезаписью удалённой истории. Нельзя применять force push. При отсутствии изменений пустой коммит не нужен.

## Один ноутбук, одна папка, работа по очереди

Это текущий сценарий команды. Сначала один участник заканчивает свою задачу, проверки, commit и push; затем второй продолжает в той же папке. Отдельное клонирование или смена аккаунта Codex для этого не нужны. Не отправляйте двум сеансам Codex независимые задания на одни файлы одновременно.

Автор коммита — тот, кто действительно выполнил работу. GitHub связывает его с аккаунтом по email, записанному в коммите. Для следующего участника нужны подтверждённые имя и email из GitHub → Settings → Emails, включая полный noreply-адрес, если он используется. Профиль напарника: DimaBegalin; указанное им имя: Dinmukhammed Begali. Подтверждённый GitHub email: `begaly05.05@mail.ru`.

Из корня Fusion, после проверки и добавления только нужных файлов:

```bash
git status
git add путь/к/изменённому/файлу
git -c user.name="Dinmukhammed Begali" -c user.email="begaly05.05@mail.ru" commit -m "Что сделано"
git push origin main
```

В этом примере следующий коммит оформляется на напарника. Для коммита текущего участника используйте обычный `git commit` (в проекте настроен `ummvvaa`, `muud.te@gmail.com`). Разовые параметры `-c` задают автора и создателя этого коммита, не меняют глобальные настройки и не выполняют вход в чужой аккаунт. Без этих параметров используется текущая настроенная личность. Для совместно сделанной задачи можно указать второго участника через `Co-authored-by: Имя <email>` в сообщении коммита. Не создавать пустые или фиктивные коммиты ради чередования.

**Аккаунт, выполняющий push, — отдельная настройка доступа.** Если правила хакатона требуют push от двух разных аккаунтов, изменения автора недостаточно. Оба участника должны иметь доступ к репозиторию и каждый сам авторизоваться локально; после этого можно настроить переключение сохранённых Git-авторизаций. Один лишь вход в GitHub в Chrome не меняет сохранённые credentials для Git. Такая настройка двух push-аккаунтов пока не выполнена.

Официальные пояснения: [email автора](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address), [соавторство](https://docs.github.com/en/pull-requests/how-tos/commit-changes/creating-a-commit-with-multiple-authors), [переключение авторизованных аккаунтов GitHub CLI](https://cli.github.com/manual/gh_auth_switch).
