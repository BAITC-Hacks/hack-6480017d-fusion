# Методика Fusion — этап 2

Версия правил: `fusion-rules-1`. Результат — структурные гипотезы для аналитика, а не установленная роль в преступной группе. Эталонной разметки нет: accuracy не измерялась. API и обучение моделей не используются.

## Воспроизведение

Из корня проекта после установки зависимостей:

```bash
.venv/bin/python -m backend.pipeline
```

Параметры: `--data data --out artifacts --top 20`. На наборе от 20 узлов минимальный топ — 20; на меньшем возвращаются все узлы. Команда последовательно проверяет весь исходный датасет, строит граф, вычисляет признаки, роли, приоритеты и кластеры, проверяет контракт выходов и записывает:

- `artifacts/nodes_roles.csv` — все входные узлы и дополнительные признаки;
- `artifacts/clusters.csv` — все кластеры, включая одиночные;
- `artifacts/top_nodes.csv` — первые 20 узлов;
- `artifacts/run_report.json` — число строк, версии, параметры, входные/выходные SHA-256 и время.

Входные parquet не изменяются. Некорректные данные приводят к ненулевому коду выхода до публикации выгрузок. Сначала все результаты записываются во временную папку и проверяются, затем заменяются отдельные файлы; транзакционная атомарность всего набора при отключении питания не реализована. `run_report.json` записывается последним и позволяет сверить SHA-256 CSV. Старые выгрузки сохраняются при отказе аудита: их актуальность нужно сверять с успешным новым отчётом.

Существующий аудит проверяет контракт конкретного кейса: июль 2026, порог 5000 KZT, исходящий обход до четырёх шагов. Он не требует фиксированного числа узлов. 97 повторных строк не удаляются: они включены в суммы и число переводов. Даты используются аудитом; скорость транзита или время удержания средств на этом этапе не вычисляются.

## Признаки

Граф направленный. Все `gid` из nodes добавляются до рёбер. `gid/src/dst` никогда не преобразуются во float: целые Python/int64, при выдаче в JSON — строки. CSV хранит десятичные целые; Excel может округлить их при автоматическом импорте, поэтому столбцы идентификаторов импортировать как текст.

| Признак | Определение |
|---|---|
| in_deg / out_deg | Число разных плательщиков / получателей, без самого узла |
| counterparties | Размер объединения плательщиков и получателей |
| in_kzt / out_kzt | Суммы входящих / исходящих внутри наблюдаемого графа |
| in_tx / out_tx | Число входящих / исходящих переводов из n_tx, с повторами |
| pass_through | out_kzt / in_kzt, пусто при нулевом входе |
| ratio_usable | Не seed, положительный вход, нет перевода самому себе; это лишь допустимость эвристики, не полнота баланса |
| pagerank | Направленный PageRank с весом sum_kzt, alpha=0.85, tol=1e-12, max_iter=1000 |
| seed_reach | Число разных seed, из которых узел достижим по направлению переводов за ≤4 шага; собственный seed не считается |
| direct_seed_senders | Число разных непосредственных плательщиков-seed |
| truncated_by_depth | depth=4 и нет наблюдаемых исходящих рёбер |
| is_isolated | В графе нет ни входящих, ни исходящих рёбер |

seed_reach не приписывает узлу конкретные деньги seed и не доказывает связь лиц; это только достижимость. Переходы по циклу не увеличивают число одного seed. Self-loop учитывается в суммах и n_tx, но не создаёт контрагента, не используется для гипотезы транзита и не связывает кластеры. В фактическом наборе self-loop нет.

## Роли и разрешение конфликтов

Правила применяются сверху вниз; первое сработавшее определяет основную роль. `rule_id` хранит выбранное правило. В `evidence` — не более 200 символов с конкретными признаками. Пороговые значения находятся в `backend/analysis_config.py`.

| Порядок | Роль / rule_id | Условие |
|---:|---|---|
| 1 | peripheral / isolated | Нет рёбер |
| 2 | peripheral / boundary | truncated_by_depth; неизвестно, идут ли деньги дальше |
| 3 | coordinator | in_deg≥3, out_deg≥2, seed_reach≥2 и pagerank≥P95 |
| 4 | distributor | out_deg≥10 |
| 5 | transit | ratio_usable, in_deg>0, out_deg>0 и out/in∈[0.8;1.2] |
| 6 | consolidator | ratio_usable, in_deg≥3 и out/in<0.8 |
| 7 | terminal | Не seed, нет self-loop, in_deg>0, out_deg=0, depth<4 |
| 8 | peripheral / no_rule | Остальные случаи |

P95 — 95-й процентиль PageRank среди неизолированных узлов вне обрезанной границы; линейная интерполяция pandas. Порог записан в run_report. Если таких узлов нет, правило coordinator выключено. Coordinator означает кандидата в структурно связующие узлы, а не установленного организатора. Пороги 3 плательщика и 10 получателей выбраны как простые защищаемые признаки схождения/веера, а не обучены на размеченных данных.

Кандидат terminal означает только наблюдаемое окончание цепочки до глубины 4 за данный месяц и выше порога переводов. Даже здесь нельзя утверждать, что деньги остались на счёте: внешние/мелкие/поздние переводы отсутствуют. На depth=4 используется консервативная периферийная роль; это может пропустить реальные структурные роли на границе, поэтому числовые признаки сохраняются для ручной проверки.

При пересечении признаков coordinator имеет приоритет над distributor, distributor — над transit, consolidator — над terminal. Узлы с несколькими наблюдаемыми паттернами получают только одну основную роль; отсутствие второй роли не означает отсутствия её признаков.

## role_score

Это шкала силы выполнения выбранного правила, не вероятность виновности и не калиброванная уверенность модели. `min(x,1)` ограничивает вклад. Формулы эвристические, не подгонялись под эталон.

| Правило | Формула |
|---|---|
| isolated | 0.10 |
| boundary | 0.15 |
| no_rule | 0.20 |
| terminal | 0.55 |
| coordinator | 0.55 + 0.20×min(seed_reach/5,1) + 0.15×min(in_deg/10,1) |
| distributor | 0.55 + 0.35×min(out_deg/30,1) |
| transit | 0.60 + 0.25×max(0,1−abs(out/in−1)/0.2) |
| consolidator | 0.55 + 0.20×min(in_deg/10,1) + 0.15×(1−(out/in)/0.8) |

Низкий peripheral score означает недостаток положительных свидетельств для специальной гипотезы, а не вероятность принадлежности к классу peripheral. Округление score — до 6 знаков.

## priority_score

Приоритет определяет порядок ручного просмотра. Он не выводится из текста LLM или ярлыка роли.

Для неотрицательного признака `L(x)=log(1+x)/max(log(1+x))`; если весь признак нулевой, его нормированный вклад равен нулю. Для PageRank используется `P=PR/max(PR)`, предварительно обнулив PR изолированных узлов. Максимумы рассчитываются по текущей выгрузке, поэтому оценки разных выгрузок напрямую не сопоставимы.

```text
base = 0.30×P
     + 0.20×L(in_kzt+out_kzt)
     + 0.25×L(seed_reach)
     + 0.15×L(counterparties)
     + 0.10×L(in_tx+out_tx)
priority_score = round(base × priority_factor, 6)
```

`priority_factor=0` для изолированных, `0.5` для обрезанной границы, `1` для остальных. Эти коэффициенты — явная политика приоритизации при неполных данных, не статистически оцененная вероятность. Вход+выход — показатель наблюдаемой активности узла, не уникальный денежный оборот всей сети. Несколько коррелирующих признаков могут усиливать одни и те же крупные узлы; веса можно обсуждать с аналитиком.

Каждое взвешенное слагаемое сохраняется в `priority_*`, множитель — в `priority_factor`; score можно пересчитать из CSV. `why` содержит evidence, итоговый score и два наибольших слагаемых. Сортировка: priority_score по убыванию, затем точный gid по возрастанию; одинаковый скор не даёт случайный порядок.

## Кластеры

Louvain на неориентированной проекции с весом `sum_kzt(A→B)+sum_kzt(B→A)`, resolution=1.0, seed=42. Self-loop исключается из проекции. Изолированные вершины добавляются отдельными кластерами. Перед расчётом узлы и рёбра сортируются; сообщества нумеруются с 0 по убыванию размера, затем минимальному gid. Это даёт стабильный результат при перестановке строк и одинаковых версиях библиотек; кластерные ID не обещают сохраняться после изменения данных.

`sum_kzt_internal` суммирует каждое направленное исходное ребро внутри кластера ровно один раз; межкластерные переводы исключены. Это не полный оборот всех участников кластера. `top_gids` — JSON-массив максимум пяти строковых ID, по тому же приоритету. `hypothesis` — локальный шаблон с размером, seed и преобладающей ролью; назначение сообщества и совместная деятельность не считаются доказанными. Число 8 из описания кейса не задано как цель.

## Воспроизводимость и ограничения

Три CSV не содержат временных меток: повторные запуски при фиксированных входах и версиях дают одинаковые байты. Отчёт содержит измеренное время и потому сам не обязан совпадать побайтно. Суммы представлены float64 исходного датасета; CSV выводит до 12 значащих цифр, доказательства округляют KZT до целых, но сравнения правил выполняются до форматирования. Это аналитическая выгрузка, не бухгалтерский регистр.

Тесты покрывают искусственные мотивы шести ролей, ограничения seed/depth, ориентированную ограниченную достижимость, встречные веса, self-loop, изоляты, малый набор parquet, отказ на неверных агрегатах, целостность кластеров, большие ID после CSV и детерминизм. Это проверки реализации правил, не валидация реальных ролей клиентов. Пайплайн не подключён к графическому интерфейсу на этапе 2. Следующий этап — API и интерактивный граф.
